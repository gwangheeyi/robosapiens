# RMF Control UI 맵 작성 및 배포 가이드

## 1. 문서 목적

이 문서는 `rmf_control_ui`에서 창고 맵을 작성하는 순서와 `배포하기` 버튼이
실제로 수행하는 작업을 설명합니다.

Waypoint별 ROS 실행, 외부 설비 Handshake 및 정밀 도킹 구조는
[ROS 관제 시스템 Waypoint 아키텍처 매핑](ROS_CONTROL_WAYPOINT_ARCHITECTURE.md)을
참고하세요.

맵 작성과 배포는 서로 다른 작업입니다.

- **맵 작성**: 도면 위에 축척, Floor, Wall, Lane, Waypoint를 정의하고
  `building.yaml`을 만드는 과정입니다.
- **배포**: 작성 결과를 Open-RMF가 읽을 수 있는 파일로 생성·설치하고,
  Building Map Server와 Fleet Adapter가 새 파일을 사용하도록 재시작하는
  과정입니다.

따라서 화면에 맵을 모두 그렸더라도 배포하지 않으면 실행 중인 Open-RMF와
로봇은 새 맵을 사용하지 않습니다.

## 2. 사전 준비

실제 배포에는 다음 환경이 필요합니다.

- Linux 데스크톱에서 실행한 `rmf_control_ui`
- ROS 2 Jazzy: `/opt/ros/jazzy/setup.bash`
- 빌드된 Open-RMF workspace: 기본값 `$HOME/rmf_ws`
- `rmf_building_map_tools`
- Fleet Adapter 설정 파일
- 프로젝트 안의 `openrmf/scripts`와 `rmf_maps` 디렉터리

프로젝트 루트는 다음 순서로 찾습니다.

1. `RMF_ROOT` 환경 변수
2. 앱의 현재 실행 디렉터리와 상위 디렉터리

프로젝트를 다른 위치에서 실행한다면 명시적으로 지정하는 편이 안전합니다.

```bash
export RMF_ROOT=/home/gyi/robosapiens
export RMF_WS=$HOME/rmf_ws
cd "$RMF_ROOT/rmf_control_ui"
flutter run -d linux
```

## 3. 맵 작성 단계

### 3.1 도면 업로드

`도면 올리기`를 눌러 PNG 또는 JPG 도면을 선택합니다.

- 이미지 원본은 YAML의 `drawing.filename`에 기록됩니다.
- PDF와 CAD 파일은 선택할 수 있지만 Wall/Floor 자동 처리를 위해서는 PNG 또는
  JPG 변환이 필요합니다.
- 실제 배포에는 이미지 바이트가 포함된 PNG 또는 JPG가 필요합니다.

### 3.2 Measurement 설정

도면에서 실제 길이를 알고 있는 두 점을 선택하고 미터 또는 피트 값을
입력합니다. 이 값으로 픽셀 좌표를 실제 거리로 변환합니다.

축척이 잘못되면 로봇 속도, Lane 거리, 도착 판정이 모두 비정상적으로 보일 수
있으므로 실제 현장 치수와 반드시 비교해야 합니다.

맵 관리 상단의 `로봇 안전 기준` 버튼에서 도면 작성 전에도 로봇 최대 폭, 최소
회전 반경과 위치 오차·안전 여유를 미리 입력할 수 있습니다. 이 값은 맵 전체의
Lane과 벽 여유를 검증하는 기준이므로 로봇을 Spawn할 때마다 입력하지 않습니다.
여러 이동 로봇이 같은 맵을 사용하면 가장 크고 회전이 어려운 로봇을 기준으로
설정합니다.

### 3.3 Wall 인식 및 수정

`벽 인식`으로 이미지의 어두운 선을 Wall 후보로 추출합니다.

- 잘못 인식한 Wall은 지우기 도구로 제거합니다.
- 끊어진 Wall은 정점을 연결합니다.
- Wall 끝점은 실제 도면 경계에 맞게 이동합니다.
- 로봇 Lane이 Wall을 통과하지 않는지 확인합니다.

### 3.4 Floor 생성

`Floor 생성`으로 로봇이 운행할 층 영역을 만듭니다. Floor 경계에는 최소 3개의
정점이 필요합니다.

### 3.5 Lane 만들기

Waypoint를 순서대로 찍으면 Lane이 이어집니다.

**시작점이 정해지면 그다음 찍는 Waypoint는 끝점입니다.** 빈 자리를 찍으면 새
Waypoint를 만들면서 잇고, 기존 Waypoint를 찍으면 그 지점까지 잇습니다. 어느
쪽이든 방금 찍은 지점이 다음 구간의 시작점이 되므로 계속 이어 그릴 수 있습니다.

시작점이 없을 때 기존 Waypoint를 찍으면 무엇을 할지 묻습니다 — `레인 시작점으로
사용`을 고르면 거기서부터 그리기 시작하고, `Waypoint 삭제`도 이 창에서 합니다.
레인을 그리는 중에는 되묻지 않으므로, 삭제처럼 다른 일을 하려면 `Esc`로 레인을
끝낸 뒤 누르세요.

- `양방향`: 시작점과 끝점 사이를 모두 이동할 수 있습니다.
- `정방향`: 시작점에서 끝점으로만 이동합니다.
- `역방향`: 끝점에서 시작점으로만 이동합니다.
- Lane을 클릭하면 방향 변경 또는 삭제가 가능합니다.
- `Esc`를 누르면 현재 Lane 입력을 종료하고 새 시작점을 선택할 수 있습니다.

벽 여유가 모자라 Lane을 잇지 못하면 Waypoint는 그대로 두고 이유를 팝업으로
알립니다. 그 지점이 새 시작점이 되므로 이어서 그릴 수 있습니다.

모든 Waypoint가 하나의 연결된 Lane 네트워크에 포함되어야 합니다. 예를 들어
`대기17 ↔ 충전1`만 서로 연결되고 다른 Lane과 연결되지 않았다면 두 지점은
작은 섬처럼 고립되어 주 네트워크에서 접근할 수 없습니다.

### 3.6 Waypoint 설정

Waypoint를 클릭해 이름과 카테고리를 설정합니다.

- 대기: 경로 연결 및 일시 정지가 가능한 지점이며 `is_holding_point`로 내보냅니다.
  자동 제안 이름은 `대기1`, `대기2`입니다. 이름을 비워 두면 시나리오 자동
  배치가 역할을 채울 후보로 씁니다.
- 주차: 작업이 없을 때 로봇을 장시간 세워 두는 전용 자리이며 `is_parking_spot`으로
  내보냅니다. Waypoint 추가 창의 기본 카테고리이며, 자동 제안 이름은 `홈1`,
  `홈2`입니다. 이름이 `홈`으로 시작하면 관제 화면이 로봇 복귀 지점으로 잡습니다.
- 홈
- 충전
- 픽업
- 드랍오프
- 설비: 고정 로봇팔, 컨베이어 및 검사 장비의 설치 좌표이며 Lane에 연결하지 않습니다.

Waypoint 이름은 중복되지 않게 작성하는 것을 권장합니다. 화면에서는 이름이
서로 겹치지 않도록 오른쪽, 왼쪽, 위, 아래 순서로 빈 위치를 찾아 표시합니다.
Waypoint 추가 시 카테고리에 맞는 이름이 자동으로 제안되며, 추가하기 전에 원하는
현장 명칭으로 수정할 수 있습니다. 이미 사용 중인 이름은 입력 단계에서 차단됩니다.

Waypoint를 클릭해 수정 창을 열고 `Waypoint 삭제`를 선택하면 확인 후 해당
Waypoint와 연결된 모든 Lane이 함께 삭제됩니다. 잘못 삭제한 경우 실행 취소로
복원할 수 있습니다.

Waypoint 입력 모드를 종료한 상태에서는 기존 Waypoint를 마우스로 잡아 원하는
위치로 드래그할 수 있습니다. Waypoint 위에 커서를 올리면 손 모양으로 바뀌며,
끌기 시작하면 도면은 따라 움직이지 않고 Waypoint만 커서를 따라옵니다. 드래그
중에는 연결된 Lane이 커서까지 늘어나 보이고, 놓을 수 있는 자리면 초록색, 놓을 수
없는 자리면 빨간색으로 표시되므로 버튼을 놓기 전에 결과를 알 수 있습니다.

`Shift`를 누른 채 끌면 시작 위치에서 **가로 또는 세로 한 방향으로만** 움직입니다.
더 많이 끈 축이 남고 다른 축은 시작값에 묶이므로, 통로를 따라 일직선으로 늘어놓을
때 눈대중으로 맞추지 않아도 됩니다. 끌던 도중에 눌렀다 떼면 원래 위치로 돌아옵니다.

드롭하면 이름과 카테고리는 유지되고 연결된 모든 Lane의 끝점이 함께 이동합니다.
Floor 밖, 다른 Waypoint와 지나치게 가까운 위치, 또는 **끌고 있는 Waypoint에
연결된** Lane이 벽 안전거리를 침범하게 되는 위치에는 놓을 수 없으며 원래 위치가
유지됩니다. 검사 대상은 함께 움직이는 Lane뿐입니다. 맵의 다른 곳에 이미 안전거리를
침범한 Lane이 있어도 그 Lane은 거기서 고칠 문제이지 다른 Waypoint를 못 움직이게 할
이유가 아니기 때문입니다. 이동 결과는 실행 취소로 되돌릴 수 있습니다.

픽업과 드랍오프 Waypoint는 각각 이름을 Open-RMF의 `pickup_dispenser`와
`dropoff_ingestor` 속성으로 내보냅니다. 실제 dispenser/ingestor 장치 이름과
Waypoint 이름을 동일하게 설정해야 합니다.

설비 Waypoint는 이동 로봇의 nav graph 정점이 아니라 고정 장비를 화면과 작업
시스템에 배치하기 위한 좌표입니다. 설비 Waypoint를 추가하면 현재 Lane 연결이
자동으로 끝나며, Lane 없이 존재해도 고립 오류로 처리하지 않습니다. 이동 로봇이
설비와 작업할 위치에는 Lane에 연결된 픽업 또는 드랍오프 Waypoint를 별도로
만들어야 합니다.

### 3.7 Open-RMF Lane 속성

Lane을 클릭하면 다음 운영 속성을 설정할 수 있습니다.

- 이동 방향: 양방향, 시작→끝 단방향, 끝→시작 단방향
- 로봇 진행 자세: 제약 없음, 정면 주행, 후진 주행
- 속도 제한: 양수인 m/s 값
- Mutex 그룹: 좁은 통로처럼 동시에 한 대만 점유해야 하는 Lane의 공통 그룹명

새 Lane을 만들 때 중복 Lane과 벽을 교차하는 Lane은 즉시 거부됩니다. 저장된
이전 프로젝트에 잘못된 Lane이 포함되어 있어도 오류 검증에서 다시 탐지합니다.
교차 판정에는 벽을 완전히 가로지르는 경우뿐 아니라 벽 끝점 접촉, 벽과 겹치는
선분 및 로봇 반폭과 Localization 여유보다 가까운 Lane도 포함됩니다. 자동 생성
중 하나의 구간이라도 이 조건을 위반하면 일부 Lane만 남기지 않고 해당 자동 초안
전체를 적용하지 않습니다.

### 3.8 시나리오 맵 자동 완성

맵 관리의 `시나리오 맵 자동 완성`에서 다음 조건을 입력할 수 있습니다.

- 이동 로봇 수
- Home 및 충전소 수
- 상온·냉장·냉동 픽업 지점 수
- 드랍오프 지점 수
- 한 운행당 1회 적재 여부
- 작업 완료 후 빈 Home 복귀 여부

자동 완성은 사용자가 먼저 지정한 Home, 충전, 픽업 및 드랍오프 Waypoint를 운영
기준점으로 보존합니다. 입력한 목표 수량에서 이미 지정된 지점 수를 빼고 부족한
역할만 추가하므로 같은 시설을 중복 생성하지 않습니다. Home 수와 같은 수의 주차
Waypoint를 별도로 확보하며 충전소는 반드시 충전 카테고리로 지정합니다. 자동
배치가 붙이는 주차 이름은 `주차1`, `주차2`로, Waypoint 추가 창의 `홈N` 제안과
다릅니다. 모든 신규 Waypoint는 Floor 다각형 내부에만 생성됩니다.

경로는 Floor 경계에서 일정 거리를 띄우는 방식이 아니라 도면을 격자로 나눈 통행
가능 영역 위에서 계산합니다. 각 격자 칸은 Floor 내부이고, 인식된 Floor 영역에
속하며, 모든 벽에서 로봇 반폭과 Localization 여유 이상 떨어져 있을 때만 통행
가능으로 표시합니다. 그중 가장 넓은 하나의 연결 영역 안에서만 경로를 만들기
때문에 벽 뒤편이나 좁은 통로로 끊긴 구역에는 Lane을 만들지 않습니다. Floor
경계는 벽 꼭짓점의 볼록 껍질이라 실제 벽보다 바깥에 있을 수 있고, 예전처럼
경계에서 일정 거리를 띄우면 벽에는 안전거리보다 가까운 Lane이 생길 수 있습니다.

**넓은 통로는 가는 길과 오는 길을 분리합니다.** 통로 폭이 안전거리의 4배
이상이면(양쪽 벽 여유 각 1배 + 두 차선 간격 2배) 그 구간을 중앙선에서 안전거리
만큼 좌우로 벌린 단방향 Lane 2개로 만듭니다. 두 로봇이 마주쳐 서로 비켜야 하는
상황 자체가 생기지 않습니다. 폭이 부족한 구간은 기존처럼 양방향 공용 Lane 하나로
두며, 한 경로 안에서 넓은 구간과 좁은 구간이 섞여 있으면 넓은 구간만 분리하고
좁아지는 지점에서 다시 합류합니다. 분리해도 곧바로 합류해야 할 만큼 짧은
구간(안전거리 4배 미만)은 나누지 않습니다. 적용 전 확인 창에 왕복 분리된 통로
수를 표시합니다.

각 경로는 지나가는 통로의 한쪽 벽에 붙지 않고 통로 중앙에 놓입니다. 벽에 붙은
경로는 넓은 통로에서도 차선을 두 개 그릴 수 없기 때문입니다. 로봇 두 대가 안전
폭을 유지할 공간이 층 전체에 있으면 출발과 복귀 경로를 위아래로 나눈 두 줄의
단방향 Lane 순환으로 만듭니다. 공간이 부족하면 양방향 공용 1경로를 만들고 양쪽
입구 가까이에 주차 지점을 배치합니다. 단, 그 1경로가 넓어 왕복 분리된 경우에는
입구 주차 지점을 두지 않습니다. Home은 드랍오프와 가까운 후보를 우선
선택합니다. 기존 Lane 네트워크와 Lane이 없는 운영 기준점은 통행 가능 영역을
따라가는 중간점으로 연결하며, 벽에 너무 가까워 안전거리를 지킬 수 없는 지점은
연결하지 않고 적용 전 확인 창에 미연결 목록으로 표시합니다. 안전거리를 지키는
통로를 전혀 찾지 못하면 도면에서 실제로 확보되는 최대 여유 픽셀을 함께 알려주므로
로봇 폭·안전 여유 또는 길이 기준(축척) 측정을 어떤 방향으로 고쳐야 하는지
바로 확인할 수 있습니다. 적용 전
이름과 좌표를 미리 확인할 수 있으며 적용 결과와 시나리오 요약은 `.rmfproject`에
함께 저장됩니다.

자동 완성 전 기존 Waypoint 이름도 분석합니다. 이름에 `충전`, `charger`, `charge`,
`charging` 또는 `dock`이 포함되면 충전으로 인식합니다. 같은 방식으로 `home/홈`,
`drop/드랍/하차`, `pickup/픽업/상차`, `parking/park/주차`, `holding/hold/wait/대기`를
해당 운영 카테고리로 인식합니다. 고정 설비와 주차 카테고리는 이름으로 변경하지
않습니다 — 주차는 이름이 `홈N`이라 이름만 보면 홈으로 잘못 분류됩니다.

자동 생성 경로는 도면의 의미와 실제 장애물을 완전히 이해한 결과가 아닌 편집용
초안입니다. 벽 교차, 통로 중심, 회전 공간과 실제 설비 접근 방향을 사용자가
수정해야 하며, 자동 완성 후 오류 검증과 현장 저속 주행 시험을 반드시 수행합니다.

#### Codex + 오프라인 혼합 분석

전체 설정과 운영 절차는 [Waypoint·Lane 혼합형 자동 경로 지정 가이드](HYBRID_ROUTE_AUTO_PLANNING.md)를
참고하세요.

앱 시작 환경에 `ROBOSAPIENS_CODEX_MAP_ENDPOINT`가 설정되어 있으면 시나리오 자동
완성은 먼저 관제 서버의 Codex 맵 분석을 호출합니다. 서버에는 도면 크기, 벽 선분,
기존 Waypoint와 Lane, 운영 지점 수 및 로봇 안전 기준만 전달합니다. 응답으로 받은
Waypoint와 Lane은 앱에서 좌표 범위, 지원 카테고리, 유효한 연결 ID 및 벽 교차를
다시 검사하며 검사를 통과한 경우에만 적용 확인 창에 표시합니다. 서버 미설정,
인터넷 단절, 시간 초과 또는 안전 검증 실패 시 기존 오프라인 생성기로 자동
전환합니다.

개발용 게이트웨이는 `tools/codex_map_gateway.py`입니다. API 키는 Flutter 앱이나
프로젝트 파일에 넣지 않고 게이트웨이 프로세스의 환경변수로만 제공합니다.

```bash
export OPENAI_API_KEY="..."
python3 tools/codex_map_gateway.py
```

Flutter 앱을 실행하는 셸에는 다음 주소를 설정합니다.

```bash
export ROBOSAPIENS_CODEX_MAP_ENDPOINT="http://127.0.0.1:8787/v1/map/analyze"
flutter run -d linux
```

모델은 기본적으로 비용과 품질의 균형을 위한 `gpt-5.6-terra`를 사용합니다. 서버의
`ROBOSAPIENS_CODEX_MODEL`로 다른 허용 모델을 지정할 수 있습니다. 완전 오프라인
운영에서는 두 환경변수를 설정하지 않으면 됩니다.

## 4. 검증과 경로 추천

### 4.1 오류 검증

오류 검증은 다음 항목을 확인하며 문제가 남아 있으면 YAML 내보내기와 배포를
중단합니다.

- 0 길이 및 중복 Lane
- 벽을 통과하는 Lane
- 분리된 Lane 네트워크와 고립된 Waypoint
- 단방향을 적용했을 때 진입 또는 복귀할 수 없는 Waypoint
- 중복 Waypoint 이름
- 설정한 최소 회전 반경의 2배보다 짧은 Lane
- Lane 중심선과 벽 사이가 `로봇 폭/2 + 위치 오차·안전 여유`보다 좁은 구간

오류 검증 창의 `로봇 안전 기준`에서 최대 폭, 최소 회전 반경과 위치 오차·안전
여유를 설정할 수 있습니다. 기본값은 각각 0.6m, 0.3m, 0.1m이며 프로젝트에
함께 저장됩니다. 적재물이 돌출되는 경우 적재 상태의 최대 폭을 입력해야 합니다.

상단의 `오류 검증` 버튼은 현재 편집 상태에서 다음 항목을 검사합니다.

- Measurement 누락
- Floor 정점 부족
- Lane 누락
- 시작점과 끝점이 같은 Lane
- 주 네트워크에서 분리된 Waypoint
- 중복된 Waypoint 이름

검증 결과는 팝업으로 표시되며 `결과 복사`로 전체 내용을 복사할 수 있습니다.
배포를 막는 Warning이 있으면 먼저 맵을 수정해야 합니다.

### 4.2 경로 추천

`경로 추천` 버튼은 다음 후보를 계산합니다.

- 분리된 Lane 구역을 주 네트워크와 연결하는 Lane
- 대기 Waypoint의 막다른 경로에 추가할 우회 Lane

Wall과 교차하는 후보는 추천에서 제외됩니다. 팝업에서 적용할 항목을 선택하고
각 Lane 방향을 수정한 뒤 `선택 적용`을 누릅니다. 추천은 기하학적·연결성
분석이므로 실제 적재물, 안전구역, 로봇 회전반경까지 보장하지 않습니다. 적용
전에 현장 통행 가능 여부를 확인해야 합니다.

## 5. 작업 저장과 YAML 내보내기

### 맵 프로젝트 저장 (MySQL)

한 대의 관제가 여러 창고를 다루므로 맵은 **프로젝트 단위로 나뉘며 지도 이름이
그 구분자**입니다. 프로젝트가 다르면 Waypoint, Lane, 벽, 축척, 로봇 안전 기준이
전부 별개입니다.

`프로젝트 저장`은 지금 편집 상태를 MySQL `robosapiens` 데이터베이스의
`map_projects` 테이블에 지도 이름으로 저장합니다. `프로젝트 열기`는 저장된
프로젝트 목록에서 하나를 골라 그 상태를 그대로 복원합니다. 목록에는 Waypoint
수, Lane 수, 도면 이름과 마지막 저장 시각이 표시됩니다.

**같은 지도 이름이 이미 있으면 저장 전에 묻습니다.** 그 프로젝트의 저장된 내용
(Waypoint 수, Lane 수, 마지막 저장 시각)을 함께 보여 주고 다음 중에서 고르게
합니다.

- `<이름> 덮어쓰기`: 기존 프로젝트를 지금 작업으로 완전히 교체합니다. 되돌릴 수
  없습니다.
- `다른 이름으로 저장`: 새 이름을 입력받아 별개의 프로젝트로 만듭니다. 입력한
  이름도 이미 쓰고 있으면 다시 묻습니다.
- `취소`: 저장하지 않습니다.

저장 구조는 `db/schema.sql`에 있습니다. `map_projects.payload`가 복원의 원본이며
도면 이미지와 벽·바닥 마스크까지 통째로 들고 있습니다.

그 옆에 **바로 꺼내 쓸 수 있는 형태로도** 함께 보관합니다. 전부 payload에서 다시
뽑아낸 사본이고 저장할 때마다 새로 채우므로 원본과 어긋나지 않습니다.

| 열 · 표 | 무엇 | 왜 |
|---|---|---|
| `drawing_bytes` `drawing_extension` `drawing_width` `drawing_height` | 도면 원본 이미지 | 수백 KB짜리 JSON을 파싱하지 않고 이미지만 바로 꺼내기 위해 |
| `building_yaml` `building_yaml_name` | Open-RMF `building.yaml` | 배포 도구가 Flutter 앱을 열지 않고 바로 집어가기 위해 |
| `map_project_waypoints` `map_project_lanes` | Waypoint·Lane 목록 | "이 맵의 주차 자리가 어디인가"를 SQL로 묻기 위해 |

`building_yaml`은 맵이 아직 YAML로 만들 수 있는 상태가 아니면 `NULL`입니다.
그래도 프로젝트 저장 자체는 막지 않습니다 — 작업 중인 맵을 저장하지 못하게 하는
것이 더 나쁩니다. `프로젝트 열기` 목록에 `YAML 보관됨`/`YAML 없음`으로 표시됩니다.

```sql
-- 특정 맵의 주차(복귀) 지점만 조회
SELECT w.name, w.x, w.y
FROM map_project_waypoints w
JOIN map_projects p ON p.id = w.project_id
WHERE p.map_name = '창고 1층' AND w.category = '주차';
```

### 작업도 프로젝트에 속합니다

대시보드의 작업(`rmf_ui_tasks`)과 그 이력은 맵 프로젝트에 귀속됩니다. 작업
단계가 그 맵의 Waypoint 좌표와 이름을 그대로 담기 때문입니다 — `창고 1층`의
`홈1(12.5, -3.25)`로 가는 작업을 `창고 2층`에서 꺼내면 그 좌표는 아무 데도
가리키지 않습니다.

따라서 **열린 프로젝트가 없으면 대시보드는 비어 있는 것이 정상입니다.** 작업
목록이 표시되지 않고, 주문 자동 분류(5초 주기)도 돌지 않으며, `새 작업`을
누르면 먼저 프로젝트를 저장하라고 안내합니다. 파일에서 연 맵도 `프로젝트 저장`
으로 등록하기 전까지는 같은 상태입니다.

작업 번호는 앱이 프로젝트 안에서 매기므로 서로 다른 맵이 같은 번호를 쓸 수
있습니다. 그래서 `rmf_ui_tasks`의 기본 키가 `(map_project_id, id)` 복합키입니다.
프로젝트를 지우면 그 맵의 작업과 이력도 함께 사라집니다(외래 키 CASCADE).

주문·재고(`orders`, `lots`)는 창고 공통 원장이므로 프로젝트로 나누지 않습니다.
열린 프로젝트가 없을 때 미처리 주문은 그대로 남아 있다가, 프로젝트를 열면 그때
분류가 시작됩니다.

### 파일로 저장 (백업·이전용)

`파일로 저장`은 편집 가능한 `.rmfproject` 파일을 저장합니다. 나중에
`파일에서 열기`로 Wall, Floor, Lane, Waypoint 편집 상태를 복원할 수 있습니다.
다른 PC로 옮기거나 백업할 때 씁니다.

`다른 이름으로 저장`은 현재 편집 상태를 새 맵 이름의 `.rmfproject`로 저장합니다.
저장 후 YAML 내보내기와 배포에도 새 맵 이름이 사용됩니다.

맵 관리 화면의 작업 정보에는 현재 `.rmfproject` 이름과 대상
`.building.yaml` 이름이 표시됩니다. 로봇 및 작업 관리 화면에서도 불러온 맵 파일과
현재 사용하는 `.building.yaml`을 확인할 수 있으며, 아직 배포 전이면 별도로 표시됩니다.

### 맵 다운로드

`맵 다운로드`에서는 다음 작업이 가능합니다.

- `.building.yaml` 파일 다운로드
- YAML 전체 내용을 클립보드에 복사

생성되는 Lane에는 Open-RMF nav graph 생성을 위한 속성이 포함됩니다.

```yaml
bidirectional: [4, true]
graph_idx: [2, 0]
```

`graph_idx: [2, 0]`은 해당 Lane을 nav graph `0`에 포함한다는 의미입니다.

## 6. 배포의 의미

이 프로젝트에서 배포는 단순히 `배포 완료` 상태를 화면에 표시하는 작업이
아닙니다. 작성한 맵을 Open-RMF 실행 파일로 변환하고, 실행 중인 RMF 노드가
새 파일을 읽도록 교체하는 작업입니다.

전체 흐름은 다음과 같습니다.

```text
오류 검증
    ↓
building.yaml 및 이미지 준비
    ↓
nav graph 및 Gazebo world/model 생성
    ↓
rmf_maps/<맵 이름>에 설치
    ↓
Building Map Server 재시작
    ↓
Fleet Adapter 재시작
    ↓
/get_building_map 서비스 및 프로세스 확인
```

실제 작업은 다음 스크립트가 담당합니다.

```text
openrmf/scripts/deploy_map.sh
```

## 7. 배포 버튼의 실제 처리 순서

### 7.1 오류 검증

UI 검증을 먼저 실행합니다. Warning이 있으면 배포를 중단하고 화면 하단에 복사
가능한 메시지를 표시합니다.

배포 스크립트도 입력 파일 존재 여부와 YAML의 기본 `levels`, `name` 항목을 다시
검사합니다.

### 7.2 임시 배포 파일 생성

Flutter 앱은 운영체제 임시 디렉터리에 다음 파일을 작성합니다.

```text
<맵 이름>.building.yaml
<원본 이미지 이름>.png
```

임시 파일은 배포 명령 종료 후 삭제됩니다.

### 7.3 nav graph 생성

다음 RMF 도구를 실행합니다.

```bash
ros2 run rmf_building_map_tools building_map_generator nav \
  <맵 이름>.building.yaml nav_graphs
```

정상적으로 생성되면 다음 파일이 있어야 합니다.

```text
nav_graphs/0.yaml
```

Fleet Adapter는 이 파일을 사용해 Waypoint와 Lane 연결 관계를 계산합니다.

### 7.4 Gazebo world 및 모델 생성

다음 명령으로 시뮬레이션용 World와 층 모델을 생성합니다.

```bash
ros2 run rmf_building_map_tools building_map_generator gazebo \
  <맵 이름>.building.yaml \
  <맵 이름>.world \
  generated_models
```

이 단계는 파일을 생성하는 작업입니다. 현재 실행 중인 Gazebo World를 자동으로
교체하거나 Gazebo를 재시작하지는 않습니다.

### 7.5 프로젝트 맵 디렉터리에 설치

새 맵은 다음 위치에 설치됩니다.

```text
<프로젝트 루트>/rmf_maps/<맵 이름>/
├── <맵 이름>.building.yaml
├── <원본 이미지>
├── <맵 이름>.world
├── nav_graphs/
│   └── 0.yaml
└── generated_models/
```

같은 이름의 기존 디렉터리가 있으면 먼저 다음 위치로 이동합니다.

```text
rmf_maps/.backups/<맵 이름>-YYYYMMDD-HHMMSS/
```

따라서 파일 생성이 완료되기 전에 기존 맵을 바로 덮어쓰지 않습니다.

### 7.6 Building Map Server 재시작

현재 사용자 계정으로 실행 중인 `building_map_server`를 종료한 뒤 새
`building.yaml`로 시작합니다.

PID와 로그는 다음 위치에 저장됩니다.

```text
openrmf/.runtime/building_map_server.pid
openrmf/.runtime/building_map_server.log
```

Map Server는 RMF 시스템과 대시보드에 Floor, Wall, Lane, Waypoint 정보를
제공합니다.

### 7.7 Fleet Adapter 재시작

현재 사용자 계정의 RMF demo Fleet Manager와 Fleet Adapter를 종료하고 새
`nav_graphs/0.yaml`로 시작합니다.

기본 Fleet 설정은 다음 파일입니다.

```text
$RMF_WS/install/rmf_demos/share/rmf_demos/config/office/tinyRobot_config.yaml
```

실제 로봇 Fleet 설정을 사용하려면 앱을 시작하기 전에 지정합니다.

```bash
export RMF_FLEET_CONFIG=/절대/경로/my_fleet_config.yaml
```

로그와 PID는 다음 위치에 저장됩니다.

```text
openrmf/.runtime/fleet_adapter.pid
openrmf/.runtime/fleet_adapter.log
```

### 7.8 새 지도 수신 확인

배포 스크립트는 최대 약 15초 동안 다음 조건을 확인합니다.

- `/get_building_map` ROS 2 서비스가 나타나는지
- 새 Building Map Server 프로세스가 살아 있는지
- 새 Fleet Adapter launch 프로세스가 살아 있는지

모두 확인된 경우에만 UI를 `배포 완료` 상태로 변경합니다.

## 8. 환경 변수

| 변수 | 기본값 | 의미 |
| --- | --- | --- |
| `RMF_ROOT` | 현재 디렉터리에서 자동 탐색 | 프로젝트 루트 |
| `RMF_WS` | `$HOME/rmf_ws` | Open-RMF workspace |
| `RMF_FLEET_CONFIG` | Office tinyRobot 설정 | Fleet Adapter 설정 파일 |
| `RMF_SERVER_URI` | `ws://127.0.0.1:8000/_internal` | rmf-web 내부 WebSocket |
| `RMF_USE_SIM_TIME` | `true` | ROS simulation time 사용 여부 |

실제 로봇에서 실행할 때는 일반적으로 다음과 같이 설정합니다.

```bash
export RMF_USE_SIM_TIME=false
export RMF_FLEET_CONFIG=/path/to/production_fleet.yaml
```

## 9. 배포 성공 후 확인할 항목

배포 성공은 파일 생성과 RMF 노드 시작이 확인됐다는 의미입니다. 로봇 운행의
정상 동작까지 자동으로 보장하는 것은 아닙니다.

다음 항목을 추가로 확인해야 합니다.

1. 대시보드에 새 맵 이름과 `L1`이 표시되는지
2. 로봇의 현재 좌표가 맵 위의 실제 위치와 일치하는지
3. 모든 작업 Waypoint로 이동할 수 있는지
4. 충전 Waypoint에 진입하고 빠져나올 수 있는지
5. 단방향 Lane을 반대로 주행하지 않는지
6. Wall이나 안전구역을 통과하는 경로가 없는지
7. 실제 로봇의 footprint와 회전반경에 충분한 공간이 있는지

## 10. 실패 메시지와 로그

배포가 실패하면 결과 팝업과 화면 하단 Warning에 전체 로그가 표시됩니다.
`로그 복사` 또는 Warning의 `복사` 버튼을 이용할 수 있습니다.

배포 버튼을 누를 때마다 성공·실패와 관계없이 프로젝트 메인 디렉터리에 전체
배포 로그를 저장합니다.

```text
<프로젝트 루트>/map-deploy-YYYYMMDD-HHMMSS.log
```

예를 들면 다음과 같습니다.

```text
/home/gyi/robosapiens/map-deploy-20260806-143025.log
```

이 파일에는 배포 시작 시각, 맵 이름, 7단계 실행 내용, RMF 생성 도구 출력과
오류 메시지가 함께 기록됩니다.

터미널에서는 다음 로그를 직접 확인할 수 있습니다.

```bash
tail -n 100 openrmf/.runtime/building_map_server.log
tail -n 100 openrmf/.runtime/fleet_adapter.log
```

자주 발생하는 문제는 다음과 같습니다.

### `nav_graphs/0.yaml이 생성되지 않았습니다`

Lane이 없거나 Lane의 `graph_idx`가 누락된 경우입니다. UI에서 Lane을 만들고
YAML을 다시 생성합니다.

### Fleet 설정 파일을 찾을 수 없음

`RMF_FLEET_CONFIG`가 올바른 절대 경로인지 확인합니다.

### `/get_building_map` 서비스를 확인하지 못함

Building Map Server 로그에서 YAML 파싱 오류, 이미지 경로 오류, ROS domain
설정을 확인합니다.

```bash
ros2 service list | grep get_building_map
```

### 대시보드에는 새 맵이 보이지만 로봇이 움직이지 않음

다음 항목이 서로 일치하는지 확인합니다.

- Fleet Adapter의 nav graph
- Fleet 설정의 로봇 이름과 충전 Waypoint
- 로봇이 보고하는 level 이름
- `RMF_SERVER_URI`
- `ROS_DOMAIN_ID`

## 11. 백업에서 복구

배포 전 맵은 `rmf_maps/.backups`에 보관됩니다. 자동 롤백은 하지 않으므로 복구가
필요하면 RMF 서비스를 중지한 상태에서 현재 맵 디렉터리와 백업 디렉터리를
확인한 뒤 이전 버전을 복원해야 합니다.

백업 경로를 잘못 선택하면 현재 맵을 잃을 수 있으므로 디렉터리 이름과 생성
시각을 확인하고 작업하십시오.

## 12. 현재 배포 범위와 제한

- 실제 배포는 Linux 데스크톱 앱에서만 지원합니다.
- 웹 앱은 보안상 로컬 스크립트와 ROS 2 프로세스를 실행할 수 없습니다.
- World와 모델은 생성하지만 실행 중인 Gazebo를 자동 재시작하지 않습니다.
- 기본 Fleet 설정은 Office `tinyRobot` 데모용입니다. 실제 로봇에는 운영 Fleet
  설정을 반드시 지정해야 합니다.
- `/get_building_map` 확인은 Map Server의 서비스 가용성을 검사합니다. 실제
  로봇의 주행 성공 여부는 별도의 현장 테스트가 필요합니다.
- 배포 중 Map Server와 Fleet Adapter가 재시작되므로 진행 중인 RMF 작업에
  영향을 줄 수 있습니다. 운영 중인 로봇을 안전 상태로 전환한 뒤 배포하십시오.
